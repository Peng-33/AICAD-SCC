# ADR-020: LLM intent / provider integration

- Status: Accepted
- Date: 2026-08-11
- Related: ADR-018 (DSL), ADR-019 (tool calling), `apps/scc-ui/lib/engineering-intent.mjs`

## Background

Phases 1–5 built two stable, LLM-free front ends: AICAD DSL (NewDesign) and
Tool Calling (EditDesign), both converging on `EngineeringCommand`. Phase 6
adds the LLM intent layer in front of them. The LLM is a controlled
intent-to-protocol translator; it never becomes the CAD engine, never stores
state, and never computes geometry.

## Decisions

### Decision 1 — the LLM is an untrusted intent parser upstream of EngineeringCommand

Every LLM output is untrusted input. It always passes through the real
`scc-dsl` parser / `scc-tools` validator / engineering validation / lowering /
SCC before anything is applied. Failures fail closed.

### Decision 2 — NewDesign defaults to AICAD DSL

A complete design from scratch is expressed as DSL text (auditable, savable,
re-parseable) and executed via `scc engineering dsl --solve`.

### Decision 3 — EditDesign defaults to tool calls

Edits use the bounded tool surface; the model never regenerates the whole
design. Edits are applied atomically via `scc engineering tools --model …`.

### Decision 4 — engineering core is fully decoupled from providers

`scc-engineering`, `scc-dsl`, `scc-tools`, and the Rust CLI know nothing about
LLM providers. Providers live only in the Node intent layer.

### Decision 5 — the model never receives or returns a full EngineeringModel

Only a derived read-only context view is sent; the model returns DSL text or
tool calls, never model JSON.

### Decision 6 — all LLM output passes the real parser/validator

No regex-based "looks like DSL" check; the Rust `scc-dsl` / `scc-tools` are
authoritative.

### Decision 7 — missing critical parameters are UNRESOLVED, never guessed

The model must not invent critical dimensions. DSL supports
`PARAM x = UNRESOLVED`; `ASSUMED` is not used by this phase (no AI-assumption
tool).

### Decision 8 — automatic repair is bounded to at most one round

DSL/TOOL/engineering local-semantic failures get one repair with a
summarized structured error. SCC geometry failures and semantic-analysis
conflicts are **never** auto-repaired, so the model cannot "fix" confirmed
engineering data to make geometry solve.

### Decision 9 — SCC geometry failure does not auto-modify confirmed data

On `SCC-GEOM-*` / `SCC-ANAL-*`, the intent is rejected; the LLM is not asked
to adjust dimensions.

### Decision 10 — provider tool schemas come from the Phase 5 ToolRegistry

The Node side reads `scc engineering manifest` (generated by Rust
`scc-tools`). No second hand-maintained tool definition; the manifest is
verified against the registry every test run.

### Decision 11 — EngineeringContextView is derived, read-only, and minimal

Derived in Rust (`EngineeringModel::context_view`), exposed via
`scc engineering context`. It carries part/feature/parameter/constraint
summaries and unresolved ids — never ConstraintIR, GraphState, ExecutionTrace,
or Proposal internals.

### Decision 12 — provider failure / invalid output has no side effects

A provider error, invalid DSL, or invalid tool batch leaves the
`EngineeringModel` unchanged (CLI `apply_all` is all-or-nothing).

## Provider neutrality

The orchestrator depends only on `IntentProvider.complete(request) →
ProviderResult` (`text` | `tool_calls` | `clarification`). The FakeProvider
drives all CI tests without a network; the OpenAI-compatible adapter is a
transport adapter (fixture-tested) mapping internal requests to a chat
completions payload and back.

## Bridge

Node drives the real Rust pipeline through the CLI subcommands
(`scc engineering manifest|dsl|tools|context`), following the existing
SccCliAdapter temp-file pattern. The Node `parseCliError` was improved to
extract the CLI's `{"errors":[...]}` shape so the orchestrator sees the real
stage codes (e.g. `SCC-GEOM-005`) instead of a generic wrapper.

## Repair policy

- Repairable (one round): `SCC-DSL-*`, `SCC-TOOL-*`, `SCC-ENG-*` (local
  semantic, e.g. an invalid slot binding or unknown tool).
- Never repairable: `SCC-GEOM-*`, `SCC-ANAL-*`, and orchestrator rejections
  (`SCC-UI-*`: wrong mode, too many calls, output too large).

## Consequences

- New-design and edit vertical slices work end-to-end without an LLM (Fake
  provider) and the whole chain runs through the real Rust pipeline.
- Derived parameters are never manually edited by the model; the program
  recomputes them.
- Intent traces (`mode`, `provider`, `outputKind`, `validation`, `repairCount`)
  are returned for audit without storing chain-of-thought.

## Technical debt

Unchanged: Constraint SourceMap counter prediction and ConstructionCircle
export semantics remain from earlier phases. A two-pass planner for very
complex parts is explicitly deferred.
